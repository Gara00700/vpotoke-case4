# Информационная безопасность — кейс 4 «Ситуационный центр»

## Как заполнять

Даны 2 угрозы из 7, 2 меры из 7, 2 строки RBAC, 2 поля аудита.
Заполни остальное. Каждая мера должна ссылаться на ID угрозы.

## 1\. Модель угроз (заполни 5 из 7)

|ID|Угроза|Актив|Вероятность|Ущерб|
|-|-|-|-|-|
|U-1|Подмена показания датчика (ложный CRITICAL)|данные телеметрии|средняя|высокий|
|U-2|Удаление / изменение инцидента|реестр инцидентов|средняя|высокий|
|U-3|Доступ к инцидентам чужой зоны без авторизации (инженер закрывает чужой инцидент, посторонний меняет статус)|реестр инцидентов, учётные записи|средняя|высокий|
|U-4|STALE не замечен: датчик молчит, а панель показывает «норму» → пропуск сбоя (перегрев, отказ вентиляции)|данные телеметрии, поголовье|высокая|высокий|
|U-5|Дубли инцидентов от одного события (повтор пакета, дребезг датчика на границе порога)|реестр инцидентов|высокая|средний|
|U-6|Перегрузка диспетчера ложными алертами → настоящий CRITICAL пропущен|внимание диспетчера, SLA|средняя|высокий|
|U-7|Отсутствие аудита спорной операции: нельзя доказать, кто и когда закрыл инцидент или изменил зону сотрудника|журнал аудита|низкая|высокий|

**Подсказки для U-3…U-7:**

* доступ к чужой зоне без авторизации;
* STALE не замечен → пропуск сбоя;
* дубли инцидентов от одного события;
* перегрузка диспетчера ложными алертами;
* отсутствие аудита спорной операции.

## 2\. Меры защиты (заполни 5 из 7)

|ID|Угроза|Мера|Остаточный риск|
|-|-|-|-|
|U-1|подмена|HMAC-подпись события датчика (SECRET только у датчика и сервера)|низкий|
|U-2|изменение|append-only аудит + RBAC (только руководитель может закрыть)|низкий|
|U-3|чужая зона|учётные записи с ролью и закреплёнными участками; роль берётся из учётной записи, а не из запроса; инженер вне своей зоны получает `FORBIDDEN OUT_OF_ZONE`, назначить инженера чужого участка нельзя; учётными записями управляет только администратор|низкий|
|U-4|STALE не замечен|правило A-4: нет данных > 5 мин → отдельный уровень STALE (серый, не «норма») + эскалация руководителю, SLA реакции 30 мин (тест T4-5)|низкий|
|U-5|дубли|правило A-5: дедупликация location + indicator в окне 5 мин; повторный `incident_id` отклоняется `DUPLICATE_EVENT`; автоинцидент создаётся один раз на датчик (тест T4-4)|низкий|
|U-6|ложные алерты|граница нормы входит в норму; WARNING только оповещает, эскалируются лишь CRITICAL и STALE; дедупликация A-5; автоинцидент только при 2 CRITICAL за 15 мин|средний: пороги нужно уточнять на реальных данных|

**Подсказка:** каждая мера ссылается на ID угрозы из раздела 1.

## 4\. Аудит — структура события (заполни 6 полей из 9)

|Поле|Тип|Пример|Зачем|
|-|-|-|-|
|event\_id|string|evt\_0001|уникальный ID|
|entity\_type|enum|incident|тип объекта|
|entity\_id|string|inc\_001|привязка к объекту|
|action|enum|status\_changed|что сделано: created / assigned / status\_changed / closed|
|from\_status|enum, nullable|ASSIGNED|статус до перехода (пусто при создании)|
|to\_status|enum|IN\_PROGRESS|статус после перехода|
|actor|string|e\_103|кто инициировал: user\_id, `mobile` или `system`|
|at|datetime (ISO 8601, UTC)|2025-11-02T18:02:00Z|когда|
|ip|string|10.0.0.1|откуда пришёл запрос (в прототипе-CLI не пишется, нужен в сетевой версии)|

В прототипе это `audit_log.csv`: `event_id,entity_type,entity_id,action,from_status,to_status,actor,at`.

**Подсказки для остальных полей:**

* `entity\\\_id` — привязка к объекту (inc\_001).
* `action` — enum: status\_changed / assigned / created / closed.
* `from\\\_status` — статус до перехода.
* `to\\\_status` — статус после.
* `actor` — кто инициировал (e\_101).
* `at` — время (ISO 8601).
* `ip` — откуда (10.0.0.1).

**Правила аудита (ответь):**

* Как хранится журнал? (append-only / можно менять) — append-only: в коде у журнала есть только метод `add()`, изменения и удаления нет; в БД — таблица без прав UPDATE/DELETE для приложения
* Сколько хранится? — не менее 90 дней (NFR-5), для разбора спорных инцидентов — 1 год.
* Кто имеет доступ на чтение? — диспетчер, руководитель, администратор; инженер — нет. Удалять не может никто.

## 5\. Защита данных датчиков (ответь на вопросы)

**Что нельзя:**

* Принимать событие без подписи — нельзя: любой в сети сможет прислать ложный CRITICAL (U-1); ответ `SENSOR_SIGNATURE_INVALID`
* Доверять `location` из события без сверки с `sites.csv` — нельзя: инцидент «на несуществующем участке» никому не назначится; ответ `UNKNOWN_LOCATION` (T4-3)
* Хранить оригинальный секрет HMAC в коде — нельзя: код лежит в Git, ключ утечёт вместе с репозиторием

**Что можно:**

* Сверять `signature` через `hmac.compare\\\_digest` — можно и нужно: сравнение за постоянное время, подпись нельзя подобрать по времени ответа
* Хранить `SECRET` в переменной окружения — можно: ключ задаётся при запуске сервиса и не попадает в репозиторий
* Логировать только `event\\\_id` и `result`, без секретов — можно: по логу видно, какое событие отклонено, но ключ и подпись не раскрываются

**Подпись события — напиши формулу:**

payload = f"{event_id}|{time}|{location}|{indicator}|{value}".encode()
expected = "hmac:" + hmac.new(SECRET, payload, hashlib.sha256).hexdigest()
return hmac.compare\_digest(expected, event\["signature"])

SECRET = os.environ\["SENSOR_HMAC_KEY"].encode(). Подписывается каждое поле, от которого зависит severity, поэтому подменить value или location без ключа нельзя.

## 6\. Секреты и ключи (заполни)

|Секрет|Где хранится|Кто имеет доступ|Ротация|
|-|-|-|-|
|HMAC-ключ датчика|переменная окружения сервиса приёма (`SENSOR_HMAC_KEY`), в проде — хранилище секретов|только сервис приёма; люди — администратор при выпуске ключа|раз в 90 дней и сразу при замене шлюза или подозрении на утечку|
|Пароль БД|переменная окружения сервиса / хранилище секретов|только учётная запись сервиса; администратор БД — отдельный пароль|раз в 90 дней|
|Bearer-токен|выдаётся мобильному приложению при входе сотрудника, хранится в защищённом хранилище телефона|сотрудник, которому выдан; сервис проверяет|срок жизни 12 ч (смена), отзыв при отключении учётной записи|

**Правила (ответь да/нет):**

* Секреты коммитятся в Git? — нет (в репозитории нет ключей и паролей, `.gitignore` исключает выходные файлы)
* Секреты логируются? — нет
* В коде — только `os.environ`? — да (в C++ — `getenv("SENSOR_HMAC_KEY")`)

## 7\. Соответствие CIA-триаде (заполни)

|Принцип|Как реализован в кейсе|
|-|-|
|Конфиденциальность|RBAC по зонам: инженер работает только с инцидентами закреплённых участков; HMAC-ключ хранится вне кода; учётными записями управляет только администратор|
|Целостность|HMAC-подпись событий датчиков; append-only аудит; запрещённые переходы (NEW → CLOSED, CLOSED → любой) отклоняются; `indicators.csv` организатора не изменяется (проверка md5)|
|Доступность|правило A-4: молчащий датчик даёт STALE и эскалацию; дедупликация A-5 не даёт заспамить диспетчера; SLA с эскалацией при просрочке|
|Аутентификация|у каждого сотрудника своя учётная запись (`employee_id`), отключённая запись не может выполнять действия; событие датчика подтверждается подписью|
|Авторизация|роль берётся из учётной записи; таблица разрешённых переходов с ролями; проверка зоны ответственности (`OUT_OF_ZONE`)|
|Неотказуемость|каждое действие пишется в аудит с `actor` и `at`; изменения учётных записей — в `accounts_log.csv` с указанием администратора|

**Подсказка:** конфиденциальность — HMAC + RBAC по зонам; целостность — append-only аудит + проверка signature; доступность — STALE + эскалация; неотказуемость — аудит с `actor` и `at`.

## 9\. Типичные ошибки (минус баллы)

1. «У нас всё безопасно» — без угроз и мер.
2. Нет HMAC для датчика — любой может подделать CRITICAL.
3. RBAC без разграничения по зонам — диспетчер видит всё.
4. Аудит без `actor` / `at` — нельзя разобрать инцидент.
5. Секреты в коде.
6. Нет связи с CIA-триадой.
